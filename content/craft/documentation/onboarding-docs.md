Onboarding documentation helps a new teammate become productive: how to set up the project, where the important code lives, how the team works, and what to read first. Good onboarding docs answer the questions a newcomer would otherwise ask in every conversation.

A useful first page is short and ordered by what the new person needs first:

```
1. Set up: install tools, clone the repo, run the tests
2. First task: a small, safe change to try the workflow end to end
3. Map of the code: the main directories and what each one owns
4. How we work: how reviews, deploys and planning happen
5. Who to ask: owners of each area
```

Test the instructions by following them on a fresh machine, or by having a recent hire do it. Steps that were true two years ago often fail today, and a newcomer will assume the docs are wrong, not out of date.

The trade-off is that onboarding docs age quickly, and a long guide is rarely read to the end. Keep the first steps short and accurate, and link deeper material for later.

The classic mistake is writing one long document that explains everything, so the first real step is buried on page four. Lead with setup and a first task, and keep the rest in linked pages that someone can read when they need them. The newcomer's own notes, such as in an [engineering journal](/t/engineering-journal), often show the gaps you should fill.
